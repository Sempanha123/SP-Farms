For Facebook/Facebook Lite/Page workflows, restore only the account's legitimate stored device assignment,

======================================================================
PHASE 53 — CONTEXT-AWARE ACCOUNT/PAGE ACTION MODAL + STORED WORKSPACE
======================================================================

GOAL:
Make SP-Farms extremely easy to operate from the main tables.

The user should NOT need to repeatedly select the same account/Page/device inside every function.

Selection in the table is the source of context.

Examples:

Accounts table:
- select Account A
- click Actions
- open one modal
- configure Restore / Post / Reel / Story / Comments / Inbox / Backup / Release / Analytics in tabs

Pages table:
- select Page A
- SP-Farms already knows its owning/connected account and stored device binding
- click Actions
- open the same contextual modal, preloaded for Page A
- no second Page/account selector unless the user explicitly chooses "Change target"

Multi-select:
- select Account A, B, C
- open Bulk Actions modal
- selected rows are automatically the targets
- only compatible tabs/actions are enabled

======================================================================

======================================================================
6. STORED DEVICE PER ACCOUNT
======================================================================

Every account must have:

AccountDeviceBinding:
- account_id
- preferred_device_id
- preferred_provider
- preferred_app
- last_good_device_id
- last_used_device_id
- binding_status
- created_at
- updated_at

Also retain:
- actual device profile
- safe display/app preferences
- last successful restore metadata
- latest lightweight snapshot ref

When restoring:
1. use preferred/bound device if healthy
2. otherwise use configured fallback policy
3. reserve device atomically
4. start device if needed
5. wait for ADB
6. restore safe workspace preferences
7. launch preferred app
8. show auth state
9. mark Ready / Needs Re-auth / Failed

======================================================================
7. PAGE -> ACCOUNT -> DEVICE RESOLUTION
======================================================================

For Page actions:

Page
  -> AssetPermission / Account connection
  -> Account
  -> AccountDeviceBinding
  -> Device

If the account is currently active on a healthy device:
- reuse it

If not:
- restore the account workspace to its preferred/available device according to policy

After Page action completes:
- keep device reserved if more steps remain
- otherwise release according to preset

======================================================================
8. LSPOSED QA PROFILE RULE
======================================================================

Maintain two separate systems:

A. Production Facebook workspace:
- actual device identity
- actual provider/ADB data
- safe stored display/app preferences
- supported auth state

B. QA Device Profile Lab:
- synthetic test values
- user's own LSPosed QA module
- only apps/packages the operator owns or is authorized to test
- hot reload without restart

Never automatically apply QA/synthetic profile to Facebook/Facebook Lite/Page actions.

The UI should make this distinction obvious:
"Production Workspace" vs "QA Profile Lab".

======================================================================
9. HOT RELOAD FOR AUTHORIZED QA APPS
======================================================================

For QA Profile Lab only:
- account/device selection can carry assigned QA profile reference
- Push + Reload
- Verify Loaded
- Restore Default
- no emulator restart required when user's QA bridge supports hot reload

Do not make Page/Facebook actions depend on QA profile injection.

======================================================================
14. ZERO-RESELECT WORKFLOW
======================================================================

Required UX:

Accounts table:
select rows -> Actions -> configure -> Run

Pages table:
select rows -> Actions -> configure -> Run

Devices table:
select rows -> Actions -> configure -> Run

Do not send the user through:
Select account -> select Page -> select device -> select account again.

Infer what is already known.

======================================================================
15. NON-BLOCKING UI / NO FREEZE
======================================================================

This is mandatory.

Never run on the Qt GUI thread:
- ADB commands
- LDPlayer/MuMu lifecycle calls
- HTTP/Meta API calls
- database-heavy operations
- media metadata extraction
- thumbnail generation
- backup compression
- restore work
- log collection
- health checks
- packaging/export work

Use:
- persistent job engine
- worker supervisor
- Qt signals/events
- async service boundaries
- bounded executors where appropriate

UI thread responsibilities:
- render
- selection
- lightweight model updates
- user input

======================================================================
16. RESPONSIVE MODEL UPDATES
======================================================================

Use:
- QTableView
- model/view
- batch model update
- debounced filters
- thumbnail cache
- paged/lazy data
- incremental status events

Do not:
- reload whole table every heartbeat
- recreate thousands of row widgets
- call `processEvents()` as a substitute for correct async design

======================================================================
17. CANCELLATION
======================================================================

Every long operation must expose safe cancellation when possible.

Modal:
- Run button becomes running state
- progress appears in footer
- Cancel Job available
- user can close modal without killing background job
- notification center keeps reporting progress

No modal should lock the entire application during long work.

======================================================================
18. STATUS STREAMING
======================================================================

Example:

LD-01
Starting...
ADB Ready
Restoring Workspace...
Opening Facebook...
Ready

Page A
Uploading image 42%
Publishing...
Published

Use event-driven status updates.

Throttle very frequent updates to avoid rendering overload.

======================================================================
19. DEVICE HEARTBEAT ARCHITECTURE
======================================================================

Device status polling must:
- run in background
- use bounded cadence
- stagger devices
- avoid launching one thread per row
- emit changed state only
- stop cleanly on shutdown

For many devices:
- batch provider queries where possible
- cache stable metadata
- query fast-changing fields separately

======================================================================
20. MODAL STATE PERSISTENCE
======================================================================

Remember:
- last used tab
- last safe configuration per action type
- column selection
- window size
- non-sensitive defaults

Do not silently reuse high-impact destructive settings.

======================================================================
21. PRESET INTEGRATION
======================================================================

The Context Action Modal and Automation Builder share the same schemas.

A user can:
- configure action in modal
- Save as Preset
- later run the preset from selected rows

No duplicated Post/Reel/Story configuration system.

======================================================================
22. ERROR HANDLING
======================================================================

Errors should attach to:
- selected account/Page/device
- active modal tab
- underlying job

Show:
- friendly message
- technical details expandable
- Retry
- Open Error Center

Do not freeze or close the modal because one target failed.

For batch actions:
- continue eligible targets according to policy
- mark failed row
- show summary
