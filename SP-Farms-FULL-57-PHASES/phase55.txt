Target:
Production-ready Windows 11 Python desktop application.

IMPORTANT SECURITY / PLATFORM RULE:
This phase supports legitimate account maintenance for accounts the operator owns or is explicitly
authorized to manage.

Do NOT implement:
- checkpoint bypass
- locked/suspended account bypass
- recovery-code interception
- CAPTCHA/security challenge bypass
- credential theft
- session hijacking
- mass unauthorized account changes
- bulk changes that evade platform safeguards

Sensitive maintenance operations must be capability-aware, permission-aware, auditable,
and approval-gated by default.

======================================================================
PHASE 55 — ACCOUNT MAINTENANCE + SECURITY AUTOMATION
======================================================================

GOAL:
Add a complete account-maintenance workflow into the same context-aware modal and Automation Builder.

The user should be able to select one or many accounts from the Accounts table and configure:

- account health check
- authorization/session check
- primary email/phone check
- 2FA status
- connected Pages/Groups check
- profile/info refresh
- supported email changes
- supported password changes
- supported 2FA enablement
- supported profile/info changes
- session/logout controls
- post-change verification
- secure vault update
- backup/audit

The user must NOT need to reselect the same account inside each function.

======================================================================
13. SAFE DEFAULTS FOR BULK OPERATIONS
======================================================================

Read-only checks may be run across multiple selected accounts.

High-impact write operations must default to:
- Require Approval = ON
- Preview Changes = ON
- Max Concurrent Changes = conservative value
- Stop on repeated failures
- No automatic retry on authentication/security rejection unless provider says retry is safe

Examples:

Safe for bulk:
- Health Check
- Check Primary Info
- Refresh Info
- Check 2FA Status
- Collect connected asset counts

Approval-gated:
- Change Password
- Change Primary Email
- Enable/Disable 2FA
- Remove Email
- Remove Phone
- Logout Other Sessions
- Update Profile Name/Birthday
- Change Avatar/Cover

======================================================================
15. VERIFY AFTER CHANGE
======================================================================

Every supported write action should optionally verify success.

Verification examples:
- email appears and primary state updated
- password-change action returned success and subsequent supported authorization check passes
- 2FA status changed
- avatar/cover metadata changed
- profile field reflects expected value

Do not mark Success based only on clicking a UI button.

======================================================================
16. ROLLBACK / RECOVERY POLICY
======================================================================

Where a provider supports reversible metadata changes:
- record previous metadata before change
- allow manual restore action

Do not automatically reverse security changes such as password/2FA without explicit user request.

For failed changes:
- retain previous local metadata
- mark NeedsAttention
- provide safe remediation

======================================================================
17. NETWORK + DEVICE + RESTORE INTEGRATION
======================================================================

Account maintenance may require the normal workspace pipeline.

Recommended order:

1. Resolve selected Account
2. Resolve Device
3. Apply required Network Profile
4. Restore Workspace
5. Verify authorization
6. Run maintenance step
7. Verify result
8. Update vault if needed
9. Backup lightweight workspace
10. Release Device
11. Start next queued Account

If a read-only API action does not need a device:
- do not unnecessarily start an emulator

Capability engine decides execution path.
